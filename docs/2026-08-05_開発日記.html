架空道路ルーティング対応（ネットワーク前処理 + 経路形状追従）v1.0.23

dev tool 19:16 pending

概要

「架空道路を描き足しても経路がそれを通らず、エラー無しで既存ルート（例: 東名高速）が選ばれる」問題の再設計。 原因は QGIS グラフがリンク端点の一致以外で接続を作らないため、途中突き当たり・端点ズレの新規リンクが孤立していたこと。 明示的な前処理ツールで接続を作る方式とし、あわせて出力ラインがリンク実形状をなぞるようにした（コスト式は不変）。

架空道路を描画（端点で突き当て） → [NEO] ネットワーク前処理（接続・link_len） → 前処理済みレイヤで最短経路 / OD / 等時圏 → 架空道路を通過＋形状追従の出力

設計判断

判断採用理由
接続処理の置き場所 明示的な前処理ツール 変換結果を目視検証できる・全アルゴリズムに効く・毎回のグラフ構築コストを増やさない（マスター選択）
途中×途中の交差分割 行わない 立体交差＝非接続の意味を保持。接続は端点突き当たりのみ
link_len 按分 平面長比率（合計保存） 分割部分のコスト和が元 link_len と一致。幾何長そのものはコストに使わない方針と整合
グリッド量子化 floor（round 不採用） round だと許容差ちょうどの 2 点が 2 セル離れ 3x3 近傍から漏れる（自己レビューで検出・回帰テスト追加）
並行リンクの区別 辺コスト照合 同一端点のリンクが複数ある場合、登録コストと edge.cost(0) の差が最小の形状を選択
形状を引けない辺 直線フォールバック＋件数ログ 静かな失敗を防ぐ（LOG.PATH_GEOM_FALLBACK）。コストには無影響

incident tool 22:13 pending

背景

マスターの実データ（関東+静岡 274,635 リンク・平面直角 IX、始点/終点は WGS84）で 東京〜御殿場を計算すると 945,345 m という異常コスト（実距離 ~123 km）が出た。 「link_len で計算できない」問題の最終的な根本原因を Docker 実機検証で特定・修正した。

原因

層内容
根本原因 QgsVectorLayerDirector はポリラインをセグメント（頂点→頂点）ごとの辺に分割して グラフを構築し、セグメント辺ごとに cost(distance, feature) を呼ぶ。 NEO の戦略は distance（セグメント長）を捨ててフィーチャ全体の link_len を毎セグメント返していたため、 セグメント数で重複課金されていた（9 km・15 セグメントのリンク → 9 km×15）。 実データ検証で 274,635 リンクが 766,752 頂点・2,894,074 辺になり、 高コスト辺すべてが同一値 9011.06（ある 9 km リンクの link_len）を示したことが決定打
潜伏要因 1 フィーチャ = 1 セグメントの手描き・単純テストでは按分不要（×1）で正しく動くため、 単純データでは発覚しない。マスターの過去検証が小規模データ中心だったことに起因
副次問題 1 実ネットワークに link_len フィールドが無い（107 フィールド、長さ列なし）→ NEO の明示エラーで停止。 前処理ツールの「作成＋実測補完」が正攻法（これは従来通り）
副次問題 2 形状索引 Qneat3EdgeGeometryIndex（1.0.23 初期に導入）はフィーチャ端点基準で セグメント辺に 76% マッチせず。実はセグメント辺の頂点チェーンはリンク形状と厳密一致するため 索引自体不要 → 削除（誤モデル由来の複雑さを除去）
副次問題 3 前処理の接続計画が 274k リンクで O(n²) 相当 → bbox グリッド索引化（セル幅 = bbox 中央値）。 退化ジオメトリ 93 フィーチャの静かなドロップも件数警告化

対応

cost(distance, feature) で distance を読む → link_len × (d_seg / L_link) に按分 → L_link はビルダ同条件（ソース CRS + WGS84）で計測 → Σ c_e over 1 リンク = link_len が厳密成立
  • 両戦略（距離・時間）に按分＋フィーチャ全長キャッシュを実装
  • 初版は全長を平面長で取り 0.07% ずれたため、ビルダと同じ楕円体計測に揃えて厳密化（スモークで 2800.0 / 306.0 / 5000.0 / 360.0 が完全一致）
  • スモークに按分回帰（2 セグメント曲線リンク: 距離 5000 / 時間 360 s）を追加（8 ステップ化）

結論

「link_len で計算できない」問題の本質は接続ではなくコスト戦略の按分漏れだった。 前処理ツール（link_len 作成・接続）と併せて、マスターの実データで東京〜御殿場が 正常なコストで計算できることを実機確認した。グラフモデルの誤解（1 フィーチャ = 1 辺と思い込む）が 戦略・形状索引の双方を歪めていた教訓を mistakes.md に記録。
